# Architecture & Security Write-up

AgentFlow uses a relational model centered on organization ownership. `organizations` contains the quota state, `org_members` maps Nhost Auth users to an organization-specific role (`owner`, `editor`, `viewer`), and `workflows` belongs to exactly one organization. A workflow owns ordered `workflow_steps` and its `workflow_triggers`. Each execution creates one `workflow_run`, while every executed or skipped node is represented by a `step_run`. Step-run rows snapshot the position/type/name so historical execution remains understandable even if the workflow definition changes later. Supporting tables (`run_jobs`, `notification_outbox`, `workflow_inbox`, `db_write_records`) make execution and side effects asynchronous instead of coupling them to one long Action HTTP request.

There are deliberately **two authorization layers**. Layer 1 is Hasura organization isolation. Authenticated users use Nhost's standard `user` GraphQL role; owner/editor/viewer is not treated as a global JWT role because the same user could be an owner in one organization and a viewer in another. Every readable workflow/run/step table is filtered through `org_members` and `X-Hasura-User-Id`. Consequently, knowing an Org A UUID does not help an Org B user: direct GraphQL reads resolve to no row. Membership administration is additionally limited to an owner in the same organization.

Layer 2 handles operations whose safety cannot be expressed as simple row visibility. Workflow definition writes go through the `saveWorkflow` Hasura Action. Its Nhost Function receives Hasura session variables, resolves the caller's membership again, and allows owners/editors to edit normal workflow nodes. Only owners may add or alter `db_write`, `notify`, or webhook trigger definitions. A webhook plaintext secret is hashed in the save Action and only its SHA-256 verifier is persisted, so read access to trigger configuration does not reveal a credential that could bypass the viewer trigger restriction. Editors cannot bypass the rule by sending their own GraphQL request because the user role has no direct write permission to workflow definition tables. The Function also requires an internal `ACTION_SECRET` header supplied by Hasura, preventing an attacker from directly invoking the Function URL and spoofing `session_variables`.

Runs use an atomic Postgres quota reservation. `reserve_org_quota` locks the organization row and only reserves a slot if `quota_used + quota_reserved < quota_allowed`, which prevents concurrent requests from oversubscribing the last available call. The monthly period is reset inside the same locked operation. A completed run converts the reservation into usage; a failed run releases it without increasing usage.

`triggerWorkflowRun` creates a queued run and a `run_jobs` row, then returns the run ID immediately. A Hasura Event Trigger invokes the executor. The executor creates/updates `step_runs` throughout execution; `llm_call` and `http_request` each receive up to two attempts. `conditional_branch` evaluates a field from the previous output and jumps to a later position, marking bypassed steps skipped. `notify` writes to an outbox and a second Hasura Event Trigger performs the actual notification delivery. This separation makes transient retries and UI subscriptions visible and avoids holding the Action request open for the workflow's entire duration.

The `approval_gate` is intentionally a mid-execution authorization decision. When encountered, the executor sets the step to `awaiting_approval`, the overall run to `paused`, and stops. `approveStep` then loads `step_run → workflow_run → org_id`, independently checks the caller's `org_members` role, and only accepts an owner/editor from that same organization. It records `approved_by` and `approved_at`, marks the gate complete, changes the run back to `queued`, and inserts a new run job beginning at the following step. This check cannot safely be represented as a normal database write permission alone because the operation means “authorize this paused execution to continue,” not merely “update a row.”

The frontend subscribes to the run and `step_runs` by run ID. Since Hasura applies the same organization filter to subscriptions as ordinary reads, Org B cannot subscribe to Org A progress either. The UI therefore reflects `queued → running → paused → running → completed/failed` and per-step statuses without refreshing while the backend remains the source of truth for every permission decision.
